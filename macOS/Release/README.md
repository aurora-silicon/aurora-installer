# Installer release inputs

Aurora uses an independent Ed25519 catalog key. Only its raw 32-byte public key belongs in this directory. Trusted publication workflows receive the private key through the protected `INSTALLER_CATALOG_SIGNING_KEY` secret. Keep local signing credentials outside repositories and release artifacts.

`release.json` names the Stable, RC, Testing and Edge catalog URLs, default channel, trust-root fingerprint and helper identity. Regenerate it with `scripts/make-release-descriptor` when those inputs change. `test/all` checks consistency with `Packaging/identity.conf`.

Fedora Aurora Remix, Aurora ALARM and Aurora NixOS each have KDE, GNOME and minimal profiles. The app loads the selected profile from `Release/Profiles/<profile>/`. Public catalogs, signatures and descriptors are published by [aurora-distributions](https://github.com/aurora-silicon/aurora-distributions). Testing (shown as Nightly) carries development candidates. Each profile has its own Edge catalog, which has no release for a Mac until an actual qualified payload is published for that profile; Stable and RC currently contain authenticated empty catalogs. Image assembly evidence and physical qualification are recorded separately.

Prepare packaging resources from a verified delivery checkout:

```sh
python3 scripts/prepare-distribution-release.py \
  --profiles /path/to/aurora-distributions/site/installer/Profiles \
  --output /path/to/release-inputs
```

This verifies all nine catalog signatures and profile bindings before emitting any resources. Normal builds include descriptors and public keys and fetch current signed catalogs at runtime. Add `--sealed` for an explicit developer or offline build: it includes the exact verified catalog bytes and records their sequences and digests in `profile-manifest.json`. Sealed catalogs take precedence over network feeds.

What a published installer pins, per channel: **Stable** is pinned. A build given `stable-release-tag` seals that release's signed Stable catalogs, so the same app always installs the same images. **Nightly (Testing)** and **Edge** float. The published DMG seals neither, so each install reads that channel's signed catalog from its feed at install time and gets whatever was last published there. Before use the catalog must verify against the app's trust root, declare its channel (or, for Testing, be an undeclared delivery of the Testing lineage), carry a valid `edgeQualification` (Edge), and be no older than the floor in `catalog-floor.json` or the last catalog this user accepted. If the feed can't be fetched or verified, preparation stops with an error and the log names the channel; it never falls back to a sealed, older or unsigned catalog. The install log records what was resolved, in a `Resolved release:` line with the channel, feed, catalog sequence and SHA-256, floor, this Mac's payload digest and URL, and Edge's Linux and Mesa revisions. The macOS stub restore image and the firmware taken from it stay pinned in every channel (`NativeInspectionPolicy`): the boot chain, firmware and tuning extraction are qualified against that exact IPSW, and a newer one has to be qualified first. Only local payload test builds seal Testing.

Set `AURORA_ENABLE_OMARCHY=1` when preparing resources and when running `Packaging/build-app.sh` to add `omarchy-hyprland`. Opt-in requires its signed catalog alongside the nine standard profiles. Release CI sets the option to `0` and verifies the nine profiles in the finished app.

"Aurora, based on Debian testing" adds `debian-kde`, `debian-gnome` and `debian-minimal` automatically whenever the delivery directory provides their signed catalogs (all three are required together). Debian images use their own `debian-btrfs-v1` layout and are produced by [debian-aurora](https://github.com/aurora-silicon/debian-aurora).

Then pass that release directory to `Packaging/build-app.sh`. Developer packages use `AURORA_DEVELOPER_BUILD=1`, a sealed catalog and the dedicated local developer package builder; they do not imply Developer ID signing or notarization.

Device firmware and per-machine calibration are collected on the target Mac and never included in public payloads or package feeds. Model admission is governed by the signed catalog and `scripts/supported-models.json`; models awaiting a first hardware boot carry an explicit caution.

Every catalog must use schema 5 and select the built-in `native-v1` engine. Older catalogs that pin a downloaded engine archive are rejected. App and catalog updates must agree on the installation profile, payload contract and artifact hashes. App assembly, signing/notarization and physical installation/Recovery qualification remain separate release gates.

Each profile directory also gets `catalog-floor.json`, the sequence of each channel catalog this step verified: Testing from the profile's `catalog.json`, and Stable, RC and Edge from `channels/stable`, `channels/rc` and `channels/edge-alpha/catalog.signed.json` in the same checkout, each verified with the app's trust root and refused if it declares another channel or lists another profile. The legacy `channels/edge` alias is not read. The app refuses a channel's catalog below its floor, on a first run too, when no accepted catalog is stored yet; a catalog at the floor, such as the sealed one, is accepted. Below the floor with nothing newer stored, the error is `belowBuildFloor` (this installer is newer than the release server), not a rollback. The file sits inside the signed app beside the descriptor, which is unchanged. A release directory without the file has no floor, and a channel whose signed catalog is absent from the checkout has none.

The descriptor remains schema 3 and names four distinct channel endpoints, with Testing as the bundled default. The bundled default is the sealed, offline fallback, never Edge. In the standard build a new installation opens on Edge instead when the selected profile's verified Edge catalog admits this Mac and lists it as family-qualified: `edgeQualification.devices` maps the Mac's device identifier to `{"evidenceDigest": "sha256:<64 hex>"}`, the digest of a detached evidence record naming the Mac and the machine row its chip family passed. One qualified machine qualifies its family; the app checks only that the map is well formed, and which models a row covers is the signed publisher's policy. A catalog without `devices` but with `neoEvidence` qualifies only `apple,j700` (a temporary fallback for alpha.1/alpha.2 catalogs, to be removed in a follow-up PR once `fedora-kde` Edge is re-published with `devices`), and a malformed `devices` qualifies no Mac. A listed Mac that isn't family-qualified, or a catalog with no release for it, opens on Nightly; Edge can still be chosen where it is listed. An Edge catalog that cannot be fetched or verified keeps Edge chosen rather than falling back, so preparing retries it, and Check Channels Again decides that default again from the same read the menu shows. Each profile is decided once per launch, and a Release channel menu choice wins. Reset and Update Boot Loader act on an existing installation and read the channel recorded when this app installed it (by the space it occupies), or Testing when none was recorded, never the Edge default; their masthead names that channel, Edge included. Because `InstallationChannelRecordStore` is stored per-user in Application Support, running Reset or Update Boot Loader from a different macOS account finds no record and falls back to Testing (shown in the masthead). Installations made before the record existed read Testing: the lane in the installation's own `omarchy/install.conf` is on its EFI partition, which only the privileged helper mounts, and `lane=edge` from installers before alpha.22 meant today's Testing. Developer and private builds keep the bundled default. Edge's ID is `edge`; its new URL is `channels/edge-alpha/catalog.signed.json`. The older `channels/edge` URL is a legacy Testing alias for already released installers and never carries the new Edge track. A legacy three-channel descriptor is read as a development descriptor: its old default Edge resolves to Testing, while new Edge is unavailable.

A sealed catalog is usable only for its own default channel. Edge cannot reuse a sealed Testing catalog. Missing Edge endpoints, signed empty Edge catalogs and unqualified legacy development catalogs are displayed as unavailable without substituting Testing. A nonempty Edge catalog must carry signed `channel: edge` and a valid `edgeQualification` bound to the actual payload, Linux/Mesa source revisions and Git tree IDs.

Every channel's catalog declares that channel in its signed `channel` field, an empty catalog included: `scripts/publish-channels empty-catalog --channel <channel>` writes it, and `os-promote` refuses a catalog that declares another channel or none. A release set bound for more than one channel stages one signed catalog for each as `releases/<tag>/catalog.<channel>.signed.json`. The app accepts a Stable, RC or Edge catalog only when it declares that channel. A catalog that declares another channel fails verification on every channel, Edge included; on Edge only an undeclared catalog reads as not published. Testing keeps one exception for the development deliveries published before the field existed: an undeclared catalog is read as Testing only when it lists at least one Mac that is not disabled and every model is of that delivery lineage (or disabled); a lineage source must be the canonical `https://github.com/aurora-silicon/<repository>/releases/download/<tag>/<fileName>` URL byte for byte. `scripts/prepare-distribution-release.py` applies the same rule to the bundled default catalog, which must otherwise declare the descriptor's default channel; `Tests/AuroraAppleInstallerTrustCoreTests/Fixtures/legacy-testing-catalog-vectors.json` pins both implementations to the same cases. That exception goes away once those deliveries are republished with `channel: testing`.
