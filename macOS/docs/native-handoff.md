# Native Recovery handoff

The helper owns startup authorization and its durable journal. For a fresh full installation, the authenticated backend's `prepare-native-handoff` mode runs its complete preflight and both disk stages. It stops after `stub-and-esp-installed`, without requesting the owner's password or recording completion. The helper requires `nativeHandoff: helper-finalize-v1`; an older backend is refused before launch. Repair keeps its existing operation until its separate native port.

The native handoff binds the strict transcript and every checkpoint to the imported plan, device and store. It rechecks the APFS target and the ordered EFI/boot/root partitions inside the approved extent, the System/Data group and Preboot identity, the external Recovery configuration and Recovery app signature. Source-volume ownership is verified against the current System group, its APFS owners and its Preboot administrator record.

The volume icon and board-mapped EFI tree are checked against the authenticated payload, using the same tree digest as the backend. Initial root writes retain the existing flushed source-hash receipt path. Recovery retries read back all installed images, including root, without decompressing the original images. Five synthetic vectors derive their expected EFI mapping from the locked backend function; the fixture payload is tiny synthetic data, not an installable OS.

Startup selection uses the verified System device and the credential on stdin. Success requires reading back the selected APFS group. The System version filename is activated before authorization and disabled after confirmed selection; the physical-media marker is activated for Recovery. An authorization failure leaves the version active, so a retry accepts that state. Relative path operations use pinned directory descriptors without symbolic links. Inner System paths and files retain their protected ownership and permission checks, and the root of the stub System volume is held to the same rule: owned by root, no write by group or others. APFS creates a volume root `root:admin` with mode 0775, and Recovery starts the top-level entries (`Finish Installation.app`, `Aurora Installer.app`, `aura`, `.IAPhysicalMedia`) by path, so the root itself must not let anyone but root rename them.

The helper therefore makes the stub System root `root:wheel` 0755 through the descriptor it has already verified as that volume's mount point (`fchown` and `fchmod`, never by path), and refuses the volume when the root then still admits another writer. This happens when the root is opened on a writable mount and again before every operation that adds, removes or renames a name through that tree, which covers a root opened read-only and remounted writable later (Update Boot Loader). It applies to a fresh installation when the stub's files are written, and to an existing installation the next time the helper opens its System volume writable: Update Boot Loader, the Recovery handoff and its retry, startup selection for Reset, and the Recovery app update. A read-only mount is read as it is: its root can't be changed, and nothing in it can be renamed while it stays read-only. A world-writable root is refused everywhere. Volumes the installer doesn't own (the source macOS Preboot, the Hardware volume, attached firmware images) keep the earlier rule for their root, no write by others, and are never changed.

A mount that ignores ownership (`MNT_IGNORE_OWNERSHIP`) reports every owner as the caller and drops `fchown`, so none of these owner checks would prove anything there. Before an owned stub System root is checked, the helper reads the mount flags on the verified descriptor; if ownership is ignored it runs `diskutil enableOwnership` for the verified device, reads the flags and the root's owner and mode again, and refuses the volume if ownership is still ignored or the flags can't be read. The same flag check runs before every write through the tree. An owned root, and every folder a tree walks under it, is also refused when it carries an access-control entry that allows writing (deny entries are ignored); such a root is refused, not repaired.

Entries left on the volume while its root was 0775 are not trusted because the root is safe now. The Recovery app update works by path under `Aurora/`, the app bundles and the version and marker files, so before its first path step it checks every one of those names, and every folder on the way to them, through the verified tree descriptor: owned by root, no write by group or others, no write access-control entry, no symbolic link, folders where folders are expected and single-name regular files where files are. Anything else refuses the update. Once the root is protected and those checks pass, only root can rename or replace anything on those paths.

Recovery's rollback of `.IAPhysicalMedia` and the version files restores owner, mode and file flags through one descriptor opened without following a link (`fchown`, `fchmod`, `fchflags`), so the change reaches the file that was written and a link under that name is refused.

The private journal is exclusively locked through handoff. Its intent is flushed before handoff changes; evidence is flushed and atomically published without replacement before its checkpoint; completion follows last. A valid prepared checkpoint can finish recording completion without authorizing startup again. Ready, started and prepared handoffs are eligible for native recovery only when their strict plan and private evidence verify. Completed journals do not offer another authorization attempt.

For full installations, the dedicated Recovery retry enters Swift directly and does not start the backend, load its decoder or repeat firmware preparation. Failed or uncertain disk operations retain the original imported inputs. The existing helper completion path still writes the chosen encryption/lane `install.conf` to the bound ESP and preserves its recorded, unconfirmed and not-recorded outcomes.

This port replaces the final startup handoff and retry. The first two installation stages still use the catalog backend; full native disk and stub installation remain separate work. Source qualification does not establish physical installation, Recovery boot or shutdown behavior. Release catalogs must be updated coherently with the new backend capability before distribution.
