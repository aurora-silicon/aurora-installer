# Native Recovery handoff

The helper owns startup authorization and its durable journal. For a fresh full installation, the authenticated backend's `prepare-native-handoff` mode runs its complete preflight and both disk stages. It stops after `stub-and-esp-installed`, without requesting the owner's password or recording completion. The helper requires `nativeHandoff: helper-finalize-v1`; an older backend is refused before launch. Repair keeps its existing operation until its separate native port.

The native handoff binds the strict transcript and every checkpoint to the imported plan, device and store. It rechecks the APFS target and the ordered EFI/boot/root partitions inside the approved extent, the System/Data group and Preboot identity, the external Recovery configuration and Recovery app signature. Source-volume ownership is verified against the current System group, its APFS owners and its Preboot administrator record.

The volume icon and board-mapped EFI tree are checked against the authenticated payload, using the same tree digest as the backend. Initial root writes retain the existing flushed source-hash receipt path. Recovery retries read back all installed images, including root, without decompressing the original images. Five synthetic vectors derive their expected EFI mapping from the locked backend function; the fixture payload is tiny synthetic data, not an installable OS.

Startup selection uses the verified System device and the credential on stdin. Success requires reading back the selected APFS group. The System version filename is activated before authorization and disabled after confirmed selection; the physical-media marker is activated for Recovery. An authorization failure leaves the version active, so a retry accepts that state. Relative path operations use pinned directory descriptors without symbolic links. A verified volume root may use the normal group-writable mount-root mode; inner System paths and files retain their protected ownership and permission checks.

The private journal is exclusively locked through handoff. Its intent is flushed before handoff changes; evidence is flushed and atomically published without replacement before its checkpoint; completion follows last. A valid prepared checkpoint can finish recording completion without authorizing startup again. Ready, started and prepared handoffs are eligible for native recovery only when their strict plan and private evidence verify. Completed journals do not offer another authorization attempt.

For full installations, the dedicated Recovery retry enters Swift directly and does not start the backend, load its decoder or repeat firmware preparation. Failed or uncertain disk operations retain the original imported inputs. The existing helper completion path still writes the chosen encryption/lane `install.conf` to the bound ESP and preserves its recorded, unconfirmed and not-recorded outcomes.

This port replaces the final startup handoff and retry. The first two installation stages still use the catalog backend; full native disk and stub installation remain separate work. Source qualification does not establish physical installation, Recovery boot or shutdown behavior. Release catalogs must be updated coherently with the new backend capability before distribution.
