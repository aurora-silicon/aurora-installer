# Whole disk: removing macOS

Some owners want Aurora to have the whole internal disk. This is a destructive, one-way opt-in: macOS, its apps and its files are deleted, and the only way back is a DFU erase and restore. This page is the design; the user page is [aurora-distributions docs/whole-disk.md](https://github.com/aurora-silicon/aurora-distributions/blob/main/docs/whole-disk.md).

## What stays and what goes

Kept, always: Apple's iSC container (first partition: iSCPreboot with every OS's LocalPolicy, xART, Hardware), Apple's System Recovery container (last partition), this installation's startup container with its System, Data, Preboot and paired Recovery volumes, its EFI partition, the Linux partitions, other startup containers (firmware slots) and anything that isn't APFS. Deleted: exactly one APFS container holding a full macOS, recognized by a System volume plus an Update volume (installer-made startup containers have no Update volume). `diskutil apfs deleteContainer` deletes every volume in the container, so that container must hold exactly one macOS and nothing else: one System and one Data volume in the same volume group, and otherwise only macOS's own Preboot, Recovery, VM and Update volumes, each at most once. A second macOS in the same container (Apple's dual-macOS layout) or a volume someone added (no role, or any other role) refuses and names every volume in it (`WholeDiskContainer.macOSProblem`, `macos_problem` in the Linux tool). The plan lists every volume that goes.

Each OS's LocalPolicy is a per-volume-group directory in iSCPreboot, so deleting the macOS container leaves Aurora's policy untouched. A LocalPolicy whose group no longer exists is left behind and is harmless: lab Macs already carry one from deleted installs and boot normally. Measurements and citations: `traces/installer/20261121-whole-disk/README.md` on the lab store.

## Owner first

With macOS gone, every later startup-security change for Aurora (Stage 1 updates, startup firmware slots, `bputil`, `kmutil configure-boot`, `bless`) needs an owner of the startup container, authenticated in its paired Recovery. The first enrollment uses the macOS owner (`source-volume-owner` bootstrap), and that owner is deleted with macOS. So removal requires the Recovery account (Recovery Step 2) to be:

- `finalized` in its record,
- an APFS volume owner of the startup container's Data volume now (`diskutil apfs listUsers`, `RecoveryAccountInstaller.requireOwnership`),
- and the password typed at the confirmation must verify against its APFS credential (`diskutil apfs unlockVolume <data> -user <uuid> -verify`).

When the account is missing, removal stops before reading the disk and says why: with no account started, the app offers Create Recovery Account… (the existing Step 2 form) and the command names it; with one started but not authorized, both say to finish it in Startup Disk; with one whose creation was interrupted, both say to open Aurora Installer again to finish it. Only `finalized` goes ahead (`MacOSRemoval.ownerGate`).

Removal runs only in the installation's own paired Recovery (the same `bputil -d -v <group>` gate as enrollment), which proves that 1TR works before it becomes the Mac's only paired Recovery.

## Flow

Post-install ("reclaim macOS space"), from Aurora:

1. `sudo aurora-whole-disk plan`: a dry run. It reads the GPT, the APFS containers (read-only, `apfs_ro.py`) and `chosen/apfs-preboot-uuid` and `chosen/asahi,efi-system-partition` from the device tree, applies the same rule as Recovery, and prints what Recovery would delete and keep. It refuses (exit 3) when the startup container has no Aurora Recovery or no recovery account, naming the fix.
2. In the installation's paired Recovery (hold the power button, Options, Terminal): `'/Volumes/<name>/aura'` opens Aurora Installer, then Utilities → Remove macOS…; or in Terminal `'/Volumes/<name>/aura' remove-macos --dry-run`, then `'/Volumes/<name>/aura' remove-macos`. The menu item and the command run the same preparation (`prepareMacOSRemoval`) and deletion (`performMacOSRemoval`); the app shows the plan in a confirmation with Cancel as the default button and fields for the phrase and the password. Preflight, in order: paired-Recovery gate, owner record and ownership, this installation is the default startup disk, Find My off (no `fmm-mobileme-token-FMM` in `nvram -x -p`; when NVRAM can't be read removal stops), one reading of the disk planned by `MacOSRemoval.plan`. It prints the plan and the consequences, asks for the exact phrase `remove macos and all its data`, then the owner's password (verified), reads the disk again and requires the same plan, journals, resolves the macOS partition by its GPT UUID once more (it must still be the reviewed BSD name on the reviewed disk), runs `diskutil apfs deleteContainer <partition UUID>`, reads the disk again and requires that only the macOS partition went, then writes `aurora/whole-disk/removed.json` on the ESP.
3. Restart into Aurora. Before any local file system is mounted, `aurora-whole-disk-move.service` moves the startup container, the ESP and /boot into the freed extent (see below). After the mounts, `aurora-whole-disk-claim.service` (or `sudo aurora-whole-disk claim`) checks the record against the disk (removed partition absent, the record names this ESP and startup container) and moves the btrfs root onto one partition that ends where the old root ended. It records `aurora/whole-disk/claimed.json` and removes `removed.json`. When the move didn't happen, `claim` instead creates one Linux partition in the freed extent, clears the old APFS signatures on it, and adds it to the btrfs root with `btrfs device add`.

Fresh install ("whole disk" mode) on a Mac with only macOS doesn't need any of that: see Fresh whole-disk installation from recoveryOS below. Until it is complete, the way to a whole-disk Aurora is a normal installation at the largest size the installer offers, then steps 2 and 3.

## Fresh whole-disk installation from recoveryOS

The target: [iSC][Aurora startup container][EFI][Boot][Root][System Recovery], laid out once with nothing moved and one root partition. macOS goes first, from recoveryOS, and Aurora is then made in the space it leaves, so there's no claim step and no second btrfs device.

Stages:

1. **Disk (built).** `aurora-fresh-install` (`Recovery/Tools/FreshWholeDiskInstallTool.swift` over `Recovery/Sources/FreshWholeDisk.swift` and `FreshWholeDiskInstall.swift`) runs as root in recoveryOS. `FreshWholeDisk.plan` accepts only Apple's iSC first, System Recovery last and, between them, exactly one container holding a full macOS (or nothing, or the first partitions of this same layout, for a resumed run). Anything else is refused: a Mac that already has Aurora uses Remove macOS. The plan puts the startup container right where iSC ends, then the EFI partition, Boot and Root, which ends exactly where System Recovery starts. Each step is the primitive the macOS engine already uses: `diskutil apfs deleteContainer` for macOS, after the phrase `remove macos and all its data` and a second reading that must plan the same, then `diskutil addPartition <predecessor> apfs|%EFI%|%Linux% ...` with each planned size. The macOS engine relies on diskutil placing each new partition right after its predecessor; that the first one lands exactly where iSC ends (a 4 KiB, not MiB, boundary) and that Root ends exactly at System Recovery hasn't been checked on a Mac yet, and if diskutil places a partition anywhere else the stage stops at that step (after macOS is gone, so this is the first hardware row's question). After every command the disk is read again and `FreshWholeDisk.next` must move exactly one step forward. The EFI partition is formatted with `newfs_msdos`, and `boot.img` and `root.img` are streamed (from a file, or over https with curl) to the raw partitions, counted and hashed against the release's pinned size and SHA-256, then read back and hashed again. The deletion uses the macOS partition's GPT UUID, as Remove macOS does, and the stage refuses to run from macOS's own Recovery (which lives in that container). The disk alone says which partition comes next, so macOS is never deleted twice. The journal (0600) records, before each `addPartition`, the role and the partitions already there, and afterwards the new partition's GPT UUID: only partitions it records are ever formatted or written. A planned partition the journal doesn't name (a finished or used installation, or a run whose journal was lost) refuses, and nothing is written to it.
2. **Startup container (not built).** Fill the startup container in recoveryOS the way the macOS engine's stub stage does from booted macOS (volumes, the IPSW's boot files, the Recovery image, Aurora Recovery and its InstallData), then make it the startup disk. The engine's stub stage uses CryptoKit, an SMJobBless helper, staging space on macOS and macOS's Preboot list of administrators, none of which exists once macOS is gone. Porting it needs the facts that `kits/test/20261122-recovery-first` records in each recoveryOS (frameworks, `aea`, network, which container recoveryOS started from).
3. **Owner (open).** With macOS gone, no user exists who could approve the new startup disk. Apple documents no way to create a Mac's first owner without Setup Assistant. Until a hardware row shows that the startup container's own Recovery can set up its first owner on a Mac with no users, this stage stays unbuilt and nothing runs stage 1 on a real Mac: stage 1 alone would leave a Mac whose startup security nobody can change.

Where recoveryOS runs from matters for stage 1: macOS's own Recovery lives in the container being deleted, so the installer runs from System Recovery (the last container, kept).

Proof without a Mac (`tools/whole-disk/fresh-test.sh OUT`): the planner's checks, then the planner and `aurora-fresh-install` itself replayed on a sparse 251 GB image with the J473's factory table (iSC, macOS, System Recovery; 4096-byte sectors). `fresh_fake_diskutil.py` plays diskutil and newfs_msdos on the image's GPT. The tests check: a full run; the dry run and a wrong phrase change nothing; stopping right after each command kind and resuming with the journal gives the same layout with macOS deleted once, and without the journal refuses once any new partition exists; a finished, used disk with no journal refuses with nothing written; running from macOS's own Recovery refuses; a wrong root digest stops before root is marked written, and a corrected run finishes; a Linux partition beside macOS is refused with no command run. iSC and System Recovery keep their GPT entries byte for byte and their data unchanged throughout.

## From Recovery

Everything that deletes or authorizes happens in recoveryOS: enrollment, the recovery account (the owner from then on), and the removal. Recovery builds tell recoveryOS from a booted macOS by `/System/Installation/CDIS`, which only recoveryOS has (`RecoveryActions.inRecovery`); the paired-Recovery check (`bputil -d -v <group>`) then proves it is this installation's Recovery. In a normal macOS the menu item isn't there and the command refuses.

The macOS part of the installation (planning, partitioning, writing images, firmware) still runs in the macOS app. Starting the whole installer from macOS's Recovery with one command, before the Aurora installation exists, isn't built: the main app targets macOS 15 and has not been checked against recoveryOS's frameworks, and it hands privileged work to a helper it registers with launchd (SMAppService or SMJobBless); neither has been tried in recoveryOS.

## One root partition again

macOS sits before the startup container, so the freed extent is not next to the root. The end state is the normal layout anyway: iSC, startup container, ESP, /boot, root, System Recovery, with one root partition.

`move` (at start, `DefaultDependencies=no`, `Before=local-fs-pre.target`, so /boot and the ESP are not mounted yet) copies the startup container, the ESP and /boot, in that order, to the start of the freed extent, each 1 MiB aligned right after the one before. Per partition: the partition is held open exclusively (it can't be mounted meanwhile) and the whole disk is flock'ed (udev leaves it alone); the bytes are copied with O_DIRECT, fsynced, and the source and the copy are read back and compared by sha256; then one write of the table points that entry at the copy; then the kernel's partition is updated and read back once more. The tool edits the GPT itself rather than through an sfdisk dump (a dump round trip clears attribute bits 3-47 on every entry): only the planned fields of the planned entries change, the backup is written and synced before the primary, each copy's header and entries in one write with SIGTERM, SIGINT and SIGHUP held off (Linux reads only the primary GPT; a primary whose entries don't match its header would show no partitions), and both copies are read back and must hold exactly the planned entries. If the kernel can't follow a switched entry, the boot unit restarts the Mac (`--reboot-on-stale`) so /boot and the ESP are never mounted from the old place. Until the table write the old place is the live one, so a stop at any point leaves a valid partition. The firmware finds the startup container and the ESP by GPT UUID (the nvram boot volume, `chosen/asahi,efi-system-partition`), APFS addresses are relative to its container, and file systems carry no absolute disk offsets (FAT's informational hidden-sectors field keeps the old value; Linux and m1n1 don't use it), so byte-exact copies stay valid. The startup container is never mounted on Linux.

Recovery's record is on the ESP, which no unit condition can see before the ESP is mounted. `move` reads the GPT first and mounts the ESP (read-only, at a private directory under /run) only when a free extent of 1 GiB or more ends at a partition up to /boot; otherwise it does nothing. It writes claimed.json on the ESP between copies, never while the ESP itself is being copied; the GPT, not the record, says which copy is live. The record carries the plan (each partition's GPT UUID, size, old and new place, the old root's GPT UUID, name and extent), and a later run accepts the disk only when every partition is at either its old or its new place in order.

`claim` then makes a partition from the end of /boot to the old root, runs `btrfs device add` with it and `btrfs device remove` with the old root (online), and in one table write deletes the old root's entry and gives the new one the old one's GPT UUID, name, attributes and end, then `btrfs filesystem resize max`. systemd ties mounts by UUID (/home and /var subvolumes) to the device /proc/self/mountinfo names, which stays the old partition after `device remove`; taking that partition away would unmount them. So before the old partition leaves the kernel, udev re-probes both partitions, `/dev/disk/by-uuid` must name the new one, and systemd is made to re-read mountinfo until no unit needs a device unit of the old partition; if one still does, the table is finished and the file system grows at the next start (a second `claim` in the same boot leaves that partition in the kernel too). `claim` runs as `Type=exec`, so the boot never waits for it. The root keeps its GPT UUID, so anything that names it that way is right once the claim is done; between `device remove` and that table write it would point at an empty partition, so `move` refuses when the running kernel command line, fstab, crypttab, /etc/kernel/cmdline, /etc/default/grub (and, in `claim`, boot entries on mounted partitions of the disk) name the root partition by PARTUUID, PARTLABEL or kernel name. Aurora's distributions name the root by its btrfs file-system UUID, which the move keeps.

`move` refuses, and `claim` adds the freed extent as a second btrfs device as before, when the freed extent isn't directly before the startup container, other partitions sit among the startup container, ESP, /boot and root, a partition is in use, a swap file or partition is on the root, a copy is bigger than the freed extent, the root's data doesn't fit the freed extent with 1 GiB to spare, a copy doesn't match, or the root isn't on one partition. A root on dm-crypt is refused by both (adding a plain partition would store data unencrypted) and a non-btrfs root is refused; in both cases the space stays free and nothing changes. Once a partition has moved, there is no fallback: a failure stops with a message and the next start continues. If `btrfs device remove` fails twice, the claim ends with the root on two devices (it keeps working that way).

## Interruptions

- Before `deleteContainer` nothing is written except the Recovery journal `Aurora/Recovery/State/whole-disk-removal.json` (mode 0600, root; Recovery reads it back only in that state).
- If `deleteContainer` fails and the disk still equals the plan, the journal is removed: nothing changed.
- If it fails part way, running `aura remove-macos` (or Remove macOS…) again decides from the journal and a new reading (`MacOSRemoval.resume`). The journal must be schema 1 in phase `deleting` or `complete`, name this installation's ESP and startup container and the same disk, and list every kept partition with UUID, type, offset and size. Then: every other partition exactly as recorded and the macOS partition and container both still there means the deletion never started (journal removed); both gone means it finished (Linux's record is written); anything else, a missing field, or partition and container disagreeing, stops with the log.
- `claim` checks `claimed.json` first. A stop after `sfdisk --append` leaves exactly one partition named `Aurora (from macOS)` over exactly the planned 1 MiB-aligned range: the next claim checks its GPT UUID and finishes on it (anything else over the range refuses). A stop after writing `claimed.json` but before removing `removed.json` (same removed partition in both) is tidied when the claimed partition is in the root file system. Once done it reports that the space was already added.
- `move` and the root half of `claim` decide each step from the GPT and the btrfs device list, checked against the plan in `claimed.json`: a stop after a copy repeats the copy; a stop after a table write continues with the next partition (the kernel's partitions are brought in line with the GPT first, and `claim` refuses while /boot or the ESP are still where the GPT no longer has them); a stop during `btrfs device remove` repeats it (btrfs keeps the device until it is empty); a stop after the final table write only grows the file system.
- A malformed `removed.json` refuses with a message, never a traceback; the root file system's devices must be partitions of the internal disk.

## Consequences shown to the owner

macOS and macOS apps are gone. Apple software updates stop: the Mac's system firmware (iBoot1, `chosen/asahi,system-fw-version`) stays at its version, so update macOS first; Aurora's startup firmware is updated with startup-firmware slots, which need only the startup container's owner. Startup-security changes need the recovery account's password, in Aurora's Recovery. Getting macOS back means a DFU erase restore, from a second Mac (Finder or Apple Configurator) or from Linux (`idevicerestore -e -R`), followed by reinstalling Aurora.

## Tests

- `Recovery/Tests/MacOSRemovalCheck.swift` (in `Recovery/test-all.sh`): planner, freed extent, record, review/verify, the confirmation phrase, the owner step and the refusal cases on a fixture of a real M2 layout.
- `tests/test_whole_disk.py`: the Linux tool on a GPT image file with synthetic APFS containers.
- `tools/whole-disk/image-test.sh` (root): a loop-device image with 4096-byte sectors, synthetic Apple containers, real FAT/ext4/btrfs; simulates Recovery's deletion and runs the real `claim`; mode `interrupted` starts from a claim stopped after `sfdisk --append`, and both modes check the leftover-`removed.json` tidy-up. Mode `v2` runs `move` with the ESP and /boot unmounted, then `claim`, and checks the normal layout, unchanged GPT UUIDs and types, sha256-equal startup container and /boot, unchanged ESP files, one btrfs device grown by the freed size, and the data after reattaching the image; `v2-interrupted` kills the tool (SIGKILL) at each of 14 points and checks that the next start ends the same; `v2-refuse` names the root by PARTUUID in fstab, so `move` changes nothing and `claim` adds a second device; `v2-j473` uses the J473's table shape (first-lba 6, unnamed, unaligned); `v2-remove-fails` ends on two devices. Every mode sets attribute bits sfdisk can't show and checks both GPT copies raw. A Fedora 43 VM (virtio-blk, 4096-byte logical blocks, both units enabled) showed the move finishing before fsck and the /boot and ESP mounts and every mount surviving the claim.
